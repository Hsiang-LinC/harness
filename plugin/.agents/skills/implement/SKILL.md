name: implement
description: "Implement a piece of work based on a spec or set of tickets."
disable-model-invocation: false
---

Implement the work described by the user in the spec or tickets.

If the user passes a ticket reference, fetch it from the issue tracker and state its title before starting. If the reference is ambiguous, ask.

Work on an issue goes through the `harness` CLI. If the issue has no record yet, it is not ready: a request this session takes straight to bind becomes one with `harness issue intake --role none`, a record candidate with `source: {kind: "description", digest}`, a fresh subagent's review with [record-review.md](record-review.md), its final report posted as a comment on the issue and recorded by `harness review record --issue <uuid> --review record --file <record> --verdict <verdict> --report-url <comment URL>`, and `harness work bind`; a `brief` source needs the `triage` review and a Spec source the `spec` review, and `review record` refuses any other pairing; a request it does not work now, such as a capture for later, is intaken with the default role, `needs-triage`; anything else needs triage first: propose `/triage` and wait. A request to stop at some point, such as "stop before you edit any code" or "stop at a failing test", still takes this path and the claim first: the stop is a point in the steps below, never a reason to skip the record. With a bound issue, its record and the files its `authoritativeContext` names are the whole brief. Every step below reads its progress back from Linear and GitHub, so after an interruption start again with `harness work read --issue <uuid>`, which lists the current facts and available edges.

First run `harness work read --issue <uuid>`. If the ticket is already completed, go directly to step 7; otherwise continue below.

Resuming work that was stopped at its pull request, when the user asks to continue it, starts with `harness work resume --issue <uuid> --file <answers>`, since `ready-for-human` fails admission: answer each open escalation `work read` lists with the user's words; one the user has not answered waits for them.

1. `harness ticket read --issue <uuid>`. If `admission` is refused, report its code and stop; never work around it.
2. `harness work claim --issue <uuid> --owner <host>:<identifier>`. The same owner re-enters its own lease, so running it again returns the token; run it again to renew before a write more than 30 minutes after the last claim. On `CLAIM_HELD`, report who holds it and until when, and stop.
3. Work on the `branch` that `ticket read` names, created from `base` if neither a local nor a remote branch exists. Keep it in its own working tree: if a worktree already has `branch` checked out (`git worktree list`), continue there; if this checkout is already isolated for this work, such as a worktree your runtime created, check out `branch` in it; if other work may run in this checkout at the same time, create one with `git worktree add` instead of switching branches here; otherwise switch here. When you create a linked worktree yourself, retain its path and a checkout outside it in this session for completion cleanup. Run every later step from that tree. Call the Skill tool with "tdd" where possible, at pre-agreed seams. Run typechecking regularly, single test files regularly, and the full test suite once at the end.
4. Commit to that branch and push it. If `pull` is null, open the pull request from `branch` into `base` with `gh pr create`, its body written by the "pr" skill. For an issue with category `bug`, the body has `## Root cause` and `## Regression test` sections; `work merge` refuses without them.
5. Call the Skill tool with "code-review" against `base`, the record's acceptance source being the Spec. At most three rounds with fresh subagents; on `fail`, fix, push and review again. Post the final report as a PR review, run `harness ticket read --issue <uuid>` again for the `candidate`, and record it: `harness review record --issue <uuid> --review code --candidate <candidate> --verdict <verdict> --report-url <review URL> --claim <token>`. Skip this step when `code.current` is true and passing.
6. If `base` has moved past the reviewed head, such as after a parallel ticket merged into it, merge `base` into `branch`, rerun the tests, push, and repeat step 5 for the new head. Then read the `merge` edge from `harness work read --issue <uuid>`. Unresolved review threads it lists are review comments: handle them as below, then resolve each thread on GitHub. Resolve any unmet condition through the edge it names. When the edge is available (an integration-branch target), run `harness work merge --issue <uuid> --claim <token> --allow integration`. When the only unmet condition left is the default-branch target, run `harness work merge --issue <uuid> --claim <token> --allow default-branch` only if the person explicitly asked in this session to merge it; otherwise ask the person to merge in GitHub, and if you stop while waiting, run `harness work escalate --issue <uuid> --reason human-needed --decision "merge <PR URL>" --pointer <PR URL>`, then `harness work release --issue <uuid> --claim <token>`. After the person merges, or whenever `pull.merged` is already true, run `harness work complete --issue <uuid>`.
7. When `work merge` or `work complete` returns `Completed`, finish with the PR and its merge state. If the result includes `rootCause` and `regressionTest`, cite both in that reply; a null value is missing evidence to report, not a fact to invent. For a ticket already completed on entry, obtain this result with idempotent `harness work complete --issue <uuid>` directly, without resuming or claiming it. The completion reply belongs to whichever session obtains the result, including a session answering what remains after another session merged.


After successful `Completed`, before sending that reply, remove a linked worktree only if this execution created it with `git worktree add`, the PR is confirmed merged, its HEAD matches the head delivered by that PR, and `git status --porcelain --untracked-files=all --ignored=matching` is empty. Run `git worktree remove <path>` from the retained checkout, keeping the branch; preserve runtime-owned, reused, uncertain or non-clean trees, and report any skip or removal failure without force or a retry loop. For leftovers, give the short hint: `git worktree list`, then `git worktree remove <path>` for a verified clean tree and `git worktree prune` for stale metadata; never force dirty work.

To stop before the work is done, for any reason (asked to stop before editing or at the PR, a decision outside the record): commit what exists to `branch` and push it; then `harness work escalate --issue <uuid> --reason <human-needed for a stop the person asked for, judgment for a decision outside the record> --decision <what the person must decide or check> --pointer <the PR URL, else https://github.com/<owner>/<repo>/tree/<branch>, else the issue URL>`, then `work release`. Never release without the escalate, or reclaim to keep In Progress: a bare release puts the ticket back as `ready-for-agent` with its work where nobody else can see it.

Review comments on the pull request continue this work under the same claim and record: answer each on the PR, fix what is in scope, and review again, since a fix changes the head the code review covers. A finding outside the record's acceptance becomes a new `needs-triage` intake (`harness issue intake` with its default role, not `--role none`), linked from the PR reply.

A request to implement authorizes these steps as written: committing and pushing `branch` and opening its pull request are part of it, not separate permissions. Never push another branch, merge outside step 6, or change Linear outside these steps without the user's authorization. To delegate a ticket, give a subagent only its issue UUID and tell it to use "implement"; it runs every step itself, claim included.
